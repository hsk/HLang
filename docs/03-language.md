# 3. 言語の表側

## いまの言語

```text
extern fn chput(c: u8 @ a) @ 0x00a2 clobbers()   // BIOS の呼び出し。引数は A で渡す

const BASE = 0xc000
var count: u8                                    // 大域変数は固定番地

fn sum(p: u16, n: u8) -> u8 {
  var acc: u8 = 0
  while n != 0 {
    acc += mem[p]                                // メモリを直接読む
    p += 1
    n -= 1
  }
  return acc
}
```

- 型は `u8`、`u16`、`bool` と、`enum` で作る列挙型。
- 文は `var`、代入、`if`、`while`、`loop`、`for i in a..b`、`match`、`break`、`continue`、`return`。
- `data` で ROM の表、`var 名前: [型; 個数]` で RAM の配列を作れます。
- 列挙型、`match`、`next`、表と配列は [6 章](06-interpreter.md) で説明します。
- `mem[e]` と `mem16[e]` でメモリ、`port[n]` で I/O ポートを読み書きします。
- `/` と `%` は割り算と余りです。符号なしの数を 2 のべき乗の定数で割るときはシフトとマスクになり、それ以外は実行時のルーチン（8bit 用と 16bit 用。使ったものだけ ROM に入る）を呼びます。0 で割ると、商は全部のビットが 1、余りは割られる数になります。
- `i8` と `i16` は符号付きの数です。足し引きは符号なしと同じで、違うのは比べ方（`<` など）と、16bit へ広げるときに符号を保つことです。数どうしは自動で型を合わせるので、`x += dx`（`x` が u8、`dx` が i8）と書けます。符号付きの `>>` は符号ビットを保ちます（`sra`）。符号付きの `/` は 0 の方へ丸め、`%` の符号は割られる数と同じです（`-7 / 2` は `-3`、`-7 % 2` は `-1`）。絶対値どうしを符号なしのルーチンで割ってから、符号を付けます。
- `copy(dst, src, n)` はメモリを写します（`ldir`）。`outs(port, src, n)` は n バイトを続けてポートへ送ります（`otir`）。`out(port, v)` と `inp(port)` は、ポート番号を変数で選べます。どれも 1 命令になります。同じ名前の関数を自分で定義すれば、そちらが使われます。
- 文字列 `"..."` は、0 で終わるバイト列を ROM に置き、その番地になります。
- 再帰は使えません。そのおかげで、変数を固定の場所に置けます。
- `inline fn 名前(...)` と書くと、呼ぶ所に本体を展開します（最適化ありのとき）。`call` と `ret` と引数の受け渡しが消え、呼ぶ側の値と一緒に最適化されます。とても小さい関数（中間表現で 8 項まで）は、書かなくても展開します。大きい関数を展開するとコードが増えるので、どこまで展開するかは書く人が決めます。

### extern と clobbers

`extern fn` は、決まった番地にある外のルーチンです。引数ごとに渡すレジスタを書きます。`clobbers(...)` には、そのルーチンが壊すレジスタを書きます。書かなければ「全部壊す」とみなします。`clobbers()` と書けば「何も壊さない」という宣言で、呼び出しをまたいで値をレジスタに置いたままにできます。

### u8 と u16 の混ぜ方

- `u8` の値は、`u16` が要る場所で自動的に広がります。
- 逆は `as u8` と書きます。
- 式の途中の計算は、その式が置かれる場所の型で行います。`var w: u16 = a + b` は、`a` と `b` が `u8` でも 16bit で足します。

## 突き合わせテスト

[test/t_lang.ml](../test/t_lang.ml) は、同じプログラムを 3 通りに実行して出力を比べます。

1. 参照インタプリタ
2. 最適化なしでコンパイルした機械語を、エミュレータで実行
3. 最適化ありでコンパイルした機械語を、エミュレータで実行

プログラムは手で書いた例のほかに、乱数で作ります。式・代入・分岐・ループ・関数呼び出し・メモリの読み書きを混ぜた、数十行のプログラムです。

```sh
dune test                         # 既定は 100 本
HL_RANDOM=5000 dune test          # 本数を増やす
```

コンパイラの誤りは、たいていこのテストが見つけます。実際に見つかった例：

- 関数の引数を配るとき、すでに正しい場所にある値を、別の値の経由地として上書きしていた。
- 経由に使う A レジスタを、先に引数で埋めてしまっていた。

## レポート

```sh
dune exec bin/hlc.exe -- examples/game.hl --report
```

関数ごとに、コードの大きさ、引数の置き場所（探索が選んだ呼び出し規約）、壊すレジスタ、時間の上限を出します。タスクは、フレームの大きさと個数、フレームの番地をどこで持つか（HL か IX か）、「再開してから次の中断まで」の時間の上限です。最後に RAM の使い道を並べます。

```text
task zako: 110 バイト
  フレーム: 6 バイト × 4 個（フレームの番地は IX で持つ）
  再開から次の中断まで: 667 T
task track: 266 バイト
  フレーム: 9 バイト × 2 個（フレームの番地は IX で持つ）
  再開から次の中断まで: 不明（終わりの決まらないループか、上限の分からない呼び出しがある）
```

時間の上限は、出したコードをたどって、入口から `ret` までのいちばん長い道を求めたものです（[src/report.ml](../src/report.ml)）。途中に輪（ループ）があれば「不明」です。ただし `ld b,n` で始まる `djnz` のループは n 回と分かるので数えます。割り算のルーチンと、プールの `resume`（個体の数 × 本体）がそうです。タスクは `yield` のたびに `ret` するので、待ちながら回るループは輪になりません。上の `track` が不明なのは、曲のデータが「最初に戻る」だけだと、中断せずに回り続けるからです。BIOS などの外の関数を呼ぶ場合は、その時間を含まない値を「+ 外の関数の時間」と付けて出します。
