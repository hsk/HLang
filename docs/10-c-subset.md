# 10. C のサブセット（実測調査）

C フロントエンド（[11 章](11-c-frontend.md)、コマンドは `hlcc`）が受ける C の範囲を、実際のゲーム 1 本のソースを数えて決めるための調査です。11 章の実装は、この調査の「サブセット v1 の提案」に沿っています。

対象: SDCC 製 MSX ゲーム **damaxian_msx**（櫻井さんの C 版 DAMAXIAN）の全ソースを走査し、
「hlc が食えるべき C サブセット」を実測から決めるための資料。
数値はすべて機械的集計＋目視確認による実測。推定箇所は「推定」と明記した。

## 対象ソースの概要

- リポジトリ: https://github.com/hsk/damaxian_msx
- コミット: `c4be8a79e8f58924be486d70de08bfcb22f73975`（2024-07-24）
- ビルド条件（makefile 実測）: `sdcc -mz80 --opt-code-speed`、
  リンクは `--no-std-crt0 --nostdinc --nostdlib --code-loc 0x8420 --data-loc 0xd400`。
  標準ライブラリも標準 crt0 も使わず、自前 `crt0.s`（32 行）が初期化を担う。
- ファイル: `.c` 14 本 + `.h` 14 本 = **28 ファイル、4,775 行**（ほかに `crt0.s` 32 行、`bios.inc` 594 行）
  - 最大は bios.h 1,148 行（大半は BIOS/DOS/VDP のアドレス定数 `#define` と asm マクロ）
  - Sound.c 760 行、System.c 508 行、Game.c 436 行
  - pattern.c（261 行）と bg.c（52 行）は生成されたデータ表
  - 関数定義は .c 全体で約 91 個

## 実測結果

### 型

| 項目 | 実測 |
|---|---|
| 基本型 | `u8`/`u16`/`i8`/`i16` のみ（bios.h で stdint 型への typedef を定義し全域で使用。u8 の出現 280 回、u16 は 23 回） |
| 32bit 型・long | **0**（uint32_t/int32_t/long とも未使用） |
| float / double | **0** |
| 素の int | ごく少数（部分一致で 9 ヒット） |
| struct | typedef struct 5 件、struct 定義系 14 ヒット。構造体ポインタ（`ENEMY*`）と `->` アクセス 149 回 |
| union | **9 件**。Enemy.h / Bullet.h で「匿名 struct と匿名 union の入れ子」として使用（下記） |
| enum | **0**（定数は全部 `#define`） |
| const / static / extern | 127 / 136 / 46 回 |
| volatile / register | 0 / 2 回 |
| ポインタ | 1 重のみ。多重ポインタ **0**、関数ポインタ宣言 **0** |
| ポインタ配列 | あり（`static const u8* const enemySpritePatternTable[]`） |
| 関数ポインタの値としての使用 | あり：`(i16)H_timiEntry` のように関数名を整数へキャスト（main.c） |
| 多次元配列 / ビットフィールド / 可変長引数 | すべて **0** |

**固定小数点の表現が最大の特徴。** Enemy.h の実例:

```c
typedef struct {
    union {
        struct { u8 xd; u8 xi; };   /* 下位・上位バイト */
        i16 x;                      /* 16bit 固定小数点として */
    };
    ...
} ENEMY;
```

i16 の上下バイトを別々に触るため、**匿名 struct / 匿名 union メンバ**（GNU 拡張、SDCC も受理）への
依存が構造的。C フロントエンドはこれを必須で受ける必要がある。

| switch / 三項演算子 / goto | すべて **0** |

| 除算 `/` ・剰余 `%` | **0 件**（ゲーム全体が乗除算を表とシフトで回避している） |

### SDCC 拡張

出現した `__` キーワードは **3 種類だけ**:

| キーワード | 実測 |
|---|---|
| `__asm` / `__endasm` | 各 20 回（ブロック開始として 17 件 + マクロ内包分） |
| `__naked` | 14 関数 |
| `__sfr` / `__at` / `__interrupt` / `__critical` / `__data` / `__code` 等 | **すべて 0** |
| `#pragma` | **0** |

ポートや SFR に C から直接触る箇所は無く、I/O は全て asm ブロックと BIOS コール経由。
割り込みも `__interrupt` を使わず、main.c が H_TIMI フックをバイト列で書き換える方式。

その代わり、字句・意味の細部に SDCC 依存がある:

- **数値リテラルの `#` 接頭辞が C コード内に 17 件**（例: `soundRegister[0] = #0b01010101;`、Sound.c）。
  SDCC が受理する書き方で、標準 C ではない
- **二進リテラル `0b...` が 50 件**（C23 / GNU 拡張相当）
- `static const u8 const` のような const の重ね書き、重複 typedef 前提の書き方が散見される
- `__naked` の使い方は 2 種類:
  1. 本体が丸ごと asm の関数（13 関数）
  2. 本体は普通の C で、プロローグ/エピローグ省略のためだけに付けたもの（AppInitialize、App.c）
- **`__naked` + asm 関数は SDCC の呼び出し規約に暗黙依存**している。
  引数名が `SystemGetAtan2(i16 hl)`、`SystemSetSprite(u8* hl, u8* de, ...)`、
  `SystemClearSoundChannel(u8 a)` のようにレジスタ名そのもので、asm 側は
  「第 1 引数は HL（u8 なら A）」等の SDCC 規約を前提に値を読む

### インライン asm

- **総量 943 行 = 全ソースの約 20%**。ファイル別:
  | ファイル | asm 行数 | ファイル全体に占める割合 |
  |---|---|---|
  | Sound.c | 480 行 | 63% |
  | System.c | 372 行 | 73% |
  | Math.c | 80 行 | 63% |
  | bios.h | 8 行 | — |
  | main.c | 3 行 | — |
- 分類（目視）:
  - **転送**（System.c）: VRAM 書き込み/フィル、スプライト転送、ビデオレジスタ転送。LDIR や OUT のループ
  - **音**（Sound.c）: `SystemUpdateSound` 1 関数で 391 行。MML の解釈と PSG レジスタ書き込みの中核が asm
  - **入力**（System.c）: キーマトリクス読み取り
  - **計算**（Math.c）: 乱数生成（xor + add の単純なもの）、atan2（表引き込み）
  - **割り込みフック**（main.c）: 保存した旧ルーチンへの `jp`、3 行
  - **BIOS 呼び出し**（Sound.c 内など）: GICINI / WRTPSG 等を asm 内から直接 call
- asm 記法は sdasz80 系: `#` 即値、`_name` グローバル記号、`0$` 形式のローカルラベル。
  さらに bios.h で `#define` された **asm テキストマクロ**（`IFNZERO(label)`、`LDA`、`LDHL`、
  `_ldircpy` など）を asm ブロック内で展開して使う。`DI()` / `EI()` も
  `#define DI() __asm di __endasm` という C マクロ（使用 9 件）。
  System.c には `#define $ __endasm; __asm` という、asm ブロックを分割するための小細工まである

### ランタイム / ライブラリ関数

- **標準ライブラリの呼び出しは 0 件**（memcpy / memset / strlen / rand / printf 等すべて無し）。
  転送は asm の LDIR、乱数は自前実装
- SDCC ランタイムヘルパの需要（推定）: 乗算・除算が実質存在しないため、
  `__mulint` / `__divuint` 等の算術ヘルパはこのコードでは不要のはず。
  実際にリンクされるのは crt0 の初期化まわりだけと見られる（推定）
- 起動処理: 自前 `crt0.s`（32 行）が SP 設定、`_gsinit`（初期化データのコピー）→ `main` 呼び出しを行う

### 整数昇格への依存

C の昇格規則に意味が依存している代表例（実測）:

1. `trigonometricTable[(u8)(a + 0x40)]`（Math.c）— u8 の `a + 0x40` が int に昇格し、
   キャストで mod 256 に戻すことを意図的に利用
2. `i8 x = ship.x - ix->xi;`（Game.c getvec）— u8 同士の引き算の結果を i8 で受け、
   符号付きとして扱う。続く `x >>= 1` は負値の算術シフト（実装定義）にも依存
3. `i16 hl = ((i16)x << 8) | y;`（Game.c）— atan2 への引数を 16bit に詰める明示キャスト
4. `SystemGetSin` は u16 の表から i16 を返す（暗黙の符号解釈の変換）
5. `*(i16*)&((u8*)H_TIMI)[1] = (i16)H_timiEntry;`（main.c）— ポインタのパニング +
   関数ポインタの整数化
6. 全体に、u8 同士の加減算を u8 で受けて mod 256 に依存する書き方が多数ある（推定）

→ フロントエンドは「C の昇格規則をそのまま実装し、値域が証明できる箇所でのみ
HLang バックエンドが昇格を省略する」という方針が安全。意味論を HLang 流に
変えると 1・2 のような箇所が静かに壊れる。

## C サブセット v1 の提案

根拠は上記の実測。「この 1 本のゲームが通る」ことを v1 の合格条件とする。

### 必須（実測で使用あり）

- 型: `u8` / `u16` / `i8` / `i16`（stdint typedef 込み）、`void`、ポインタ（1 重）、
  構造体、**匿名 struct / union メンバ**、配列、ポインタ配列、`const` / `static` / `extern`
- 関数名・関数ポインタの整数へのキャスト、ポインタのパニング（型違いポインタ経由の読み書き）
- 制御: if / else、for（**初期化部での変数宣言**を含む）、while、do-while、return、break / continue（推定で使用あり）
- 演算: ビット演算・シフト、複合代入、++ / --、キャスト、配列添字、`.` / `->`、
  乗算（定数倍を含む一般形。除算・剰余は実測 0 だが、ヘルパ呼び出しで受けるのが無難）
- 初期化子: 配列の `{...}`、**隣接文字列リテラルの連結**による `const u8` 配列初期化
- プリプロセッサ: `#define`（定数・関数マクロ、asm テキストマクロを含む）、`#include`（ローカル + stdint.h のみで可）
- SDCC 互換の字句: 数値リテラルの `#` 接頭辞、二進リテラル `0b...`
- `sizeof`（定数式として評価できれば十分。実測 1 件）
- `__naked`、`__asm` / `__endasm` のパススルー（下記方針）
- C の整数昇格規則（意味論は C 準拠にし、最適化はバックエンド側の値域証明に任せる）

### あれば尚よい（このコードでは 0 だが、一般の MSX ゲームコードでは頻出と推定）

- switch、三項演算子、enum（いずれも実測 0。ただし「次の 1 本」で出る可能性が高い）
- `__sfr` / `__at`（実測 0。ポート直接アクセス型のコードでは必須になる）
- 関数ポインタ経由の呼び出し（実測 0）

### 対象外（実測 0、v1 では切り捨ててよい）

- 32bit 以上の型、long、float / double
- 多重ポインタ、多次元配列、ビットフィールド、可変長引数、goto
- 標準ライブラリ関数一式（呼び出し自体が存在しない）
- `#if` 系の条件コンパイル（実測 0。プリプロセッサは #define / #include のみで足りる）

## インライン asm の扱い方針案

前提: asm は全体の 20%、しかも熱い場所（転送・音）に集中している。
**v1 では asm を解釈せず、不透明ブロックとして通す。**

1. `__naked` 関数は「宣言（引数・戻り値）だけ C、体は asm テキスト」として扱う。
   呼び出し側は通常の関数として呼ぶ
2. **引数のレジスタ割り当ては SDCC 規約と互換にする。** asm 側が
   「u8 第 1 引数は A、16bit/ポインタ第 1 引数は HL、第 2 ポインタ引数は DE」等を
   前提に書かれているため、ここがずれると全ての naked 関数が壊れる。
   naked 関数の宣言に出てくる引数名（a / hl / de）は事実上の規約指定として扱う
3. 文中の `__asm` ブロック前後では、全レジスタとフラグを「不定」として扱い、
   生存中の変数はメモリに退避する。HLang の配置探索からは
   「その点では全レジスタ使用済み・HL は壊れる」として見えるのが安全側
4. asm テキストは sdasz80 記法のまま保持する（`#` 即値、`_` 接頭辞、`0$` ローカルラベル、
   `#define` による asm マクロ展開）。自前アセンブラで受けるか、
   SDCC のアセンブラ形式への変換層を挟むかは実装時に決める
5. `DI()` / `EI()` 型のマクロ asm は、プリプロセッサ展開後に同じ不透明ブロック扱いにする

## 必要なランタイム

実測ベースで最小限:

- 初期化: 初期値付きデータのコピー（gsinit 相当）と BSS ゼロクリア、SP 初期設定
  （自前 crt0.s 32 行相当の働き）
- 算術ヘルパ: このコードでは乗除算ヘルパは不要（実測）。ただしサブセットとして
  16bit 乗算・除算を受けるなら、SDCC 互換ヘルパ（`__mulint` 等）の自前実装が要る（推定）
- ライブラリ関数: 不要（呼び出し 0 件）。memcpy / memset を使うコードに広げるなら
  LDIR ベースの実装を数十行で足せる

## z88dk との差分（一般知識による付記。実測ではない）

- z88dk にはコンパイラが 2 系統ある（独自の sccz80 と、SDCC を包んだ zsdcc）。
  zsdcc なら SDCC 方言に近いが、sccz80 は別物
- sccz80 の拡張: `__LIB__`、`__FASTCALL__`（引数をレジスタで受ける指定）など
  呼び出し規約を宣言側で変える仕組みがあり、SDCC の「暗黙の規約依存」とは設計が違う
- asm の埋め込み書式も異なる（`#asm` / `#endasm` 形式や `asm("...")` 形式が混在する）
- ポート宣言（sfr）の書式も SDCC と異なる
- → C フロントエンドは「SDCC 方言」を v1 とし、z88dk（特に sccz80）は
  別方言として切り分けるべき。今回の実測はすべて SDCC 方言についてのもの

## 結論

- **フロントエンドは現実的な規模。** 対象コードが使う C は狭い:
  型は 8/16bit のみ、制御構造は if/for/while のみ、標準ライブラリ不使用、
  乗除算は実質ゼロ、プリプロセッサも #define 中心。
  「damaxian_msx 1 本を通す」サブセットなら、パーサ＋型検査は数千行級に収まる見込み（推定）
- **重い点は C の文法ではなく互換性の細部**、具体的には次の 3 つ:
  1. `__naked` + asm 関数の SDCC 呼び出し規約への暗黙依存（引数名 = レジスタ指定）
  2. asm パススルー（全体の 20%。sdasz80 記法 + asm マクロ + ブロック前後の保守的扱い）
  3. 匿名 struct/union による固定小数点のバイトアクセスと、C の昇格規則への依存
     （意味論を変えず、最適化で吸収する設計が要る）
- 逆に、恐れられていた要素（SFR 宣言、割り込み属性、ライブラリ、32bit 演算）は
  このコードでは全部ゼロだった。「コンパイルし直すだけで速くなる」実験の
  最初の的としては、かなり条件の良い相手と言える
